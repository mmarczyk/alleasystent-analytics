# Cloudflare Pages — deploy workflows for both frontends

Both AllEasystent frontends are static sites that publish to GitHub Pages
today. This directory holds the **Cloudflare Pages** version of those deploys:
one Pages project per app, both deployed from GitHub Actions with
`wrangler pages deploy`.

| App | Repo | Source | Pages project | Origin |
|---|---|---|---|---|
| Chat UI (PWA) | `mmarczyk/alleasystent` | `web/` | `alleasystent` | `https://alleasystent.pages.dev` |
| Analytics dashboard | `mmarczyk/alleasystent-analytics` | `index.html` + generated `config.js` | `alleasystent-analytics` | `https://alleasystent-analytics.pages.dev` |

## Why Actions rather than Cloudflare's Git integration

Cloudflare can build straight from a connected repo, but then `config.js` would
have to be generated by a build command configured in the dashboard, with the
backend URL and Client ID living in Cloudflare's environment variables. Driving
the deploy from Actions keeps all of that in the workflow file, next to the
vendor-asset download the chat UI needs, where it is reviewable in git. The
only thing Cloudflare holds is the API token.

## One-time setup

### 1. Two Pages projects

Cloudflare dashboard → **Workers & Pages** → **Create** → **Pages** → **Upload
assets**, which creates a *Direct Upload* project. Name them `alleasystent` and
`alleasystent-analytics`. They must exist before the first workflow run —
`wrangler pages deploy` will not create a project non-interactively.

Ignore the upload prompt; the workflows do the uploading. The free plan has no
limit on the number of projects and needs no payment method — the reason this
is simpler than Firebase Hosting, where a second site in one project requires a
billing account.

### 2. An API token

**My Profile → API Tokens → Create Token**, with the **Cloudflare Pages: Edit**
permission. Copy the token once — it is not shown again. The **Account ID** is
in the right-hand panel of the dashboard's account home.

### 3. Secrets and variables on both repos

Settings → Secrets and variables → Actions.

| Kind | Name | `alleasystent` | `alleasystent-analytics` |
|---|---|---|---|
| Secret | `CLOUDFLARE_API_TOKEN` | the token | the same token |
| Secret | `CLOUDFLARE_ACCOUNT_ID` | the account ID | the same account ID |
| Variable | `CLOUDFLARE_PROJECT` | `alleasystent` | `alleasystent-analytics` |
| Variable | `BACKEND_URL` | already set | already set |
| Variable | `GOOGLE_CLIENT_ID` | — | already set |
| Variable | `CHAT_URL` | — | `https://alleasystent.pages.dev` |
| Variable | `FRONTEND_URL` | `https://alleasystent.pages.dev` | — |
| Variable | `ANALYTICS_FRONTEND_URL` | `https://alleasystent-analytics.pages.dev` | — |

Nothing about GCP changes: no service account, no IAM, no project. The backend
stays on Cloud Run exactly as it is, and the frontends reach it over its public
HTTPS URL.

### 4. Re-point the origins (the part that actually breaks things)

Moving off GitHub Pages **changes both frontends' origins**, and three places
hardcode them:

1. **OAuth 2.0 Client ID** (GCP Console → APIs & Services → Credentials →
   Authorized JavaScript origins) — add
   `https://alleasystent-analytics.pages.dev`. Without this, Google Sign-In
   fails with `origin_mismatch` and the dashboard shows nothing.
2. **Backend CORS** — the `FRONTEND_URL` and `ANALYTICS_FRONTEND_URL` variables
   above are read by `deploy-backend.yml` into Cloud Run env vars, so **re-run
   that workflow** after setting them. Changing the variable alone does nothing
   to the running service.
3. **`CHAT_URL`** on this repo, so the dashboard's back-link points at the
   Cloudflare-hosted chat instead of GitHub Pages.

## Coexistence with the GitHub Pages workflows

The existing Pages workflows (`deploy.yml` here, `deploy-chat.yml` on
`alleasystent`) are left in place, so during the migration a push to `main`
publishes to **both** targets. That is intentional — the Pages URLs keep
working until you have verified the Cloudflare ones. Once you have, retire
Pages per repo by either deleting its workflow file or narrowing its trigger to
`workflow_dispatch:` only.

`.nojekyll` is only meaningful for GitHub Pages; the Cloudflare workflow does
not copy it into `dist/`.

## Preview deployments

Not enabled, but unlike Firebase's preview channels they would be workable
here. A Pages deploy from a branch gets a **stable** alias,
`https://<branch>.<project>.pages.dev`, so a long-lived branch's origin can be
registered in the OAuth client and in the backend's CORS allowlist ahead of
time. To turn it on, drop the `--branch=main` flag and let wrangler use the
current branch. Per-commit URLs stay unpredictable, so only the branch alias is
usable for anything that has to pass Sign-In or CORS.

## Rollback

Cloudflare keeps every deployment. Dashboard → the Pages project →
**Deployments** → the "..." menu on a previous production deployment →
**Rollback**. It is instant and needs no rebuild. Re-running the workflow on
the desired commit (`workflow_dispatch`) achieves the same from CI.
